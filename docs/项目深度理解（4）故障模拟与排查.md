# 项目深度理解(4)故障排查

## 1. 常见故障模拟

### 1.1 网络中断故障
**故障描述**：监控系统与被监控对象之间的网络连接中断，导致指标采集失败。

**模拟方法**：
- **临时禁用网络接口**：`ifdown eth0` 或 `ip link set eth0 down`
- **添加防火墙规则**：`iptables -A INPUT -s 192.168.213.142 -j DROP`
- **模拟网络延迟**：`tc qdisc add dev eth0 root netem delay 1000ms`

**预期现象**：
- Prometheus Targets页面显示目标为DOWN状态
- 告警触发：NodeDown告警
- 监控数据停止更新

### 1.2 磁盘空间满故障
**故障描述**：服务器磁盘空间不足，导致服务无法正常运行。

**模拟方法**：
- **创建大文件**：`dd if=/dev/zero of=/tmp/bigfile bs=1G count=10`
- **填充日志文件**：`yes "test" >> /var/log/syslog`
- **模拟Loki存储满**：向Loki写入大量日志数据

**预期现象**：
- Prometheus告警：HighDiskUsageCritical
- 服务日志出现"disk full"错误
- 新日志无法写入
- 容器可能重启或崩溃

### 1.3 服务崩溃故障
**故障描述**：监控组件（如Prometheus、Grafana、Alertmanager等）崩溃或停止运行。

**模拟方法**：
- **强制停止容器**：`docker stop prometheus`
- **终止进程**：`pkill -9 prometheus`
- **模拟OOM**：使用stress工具消耗内存，触发OOM Killer

**预期现象**：
- 容器状态变为Exited
- Prometheus Targets显示为DOWN
- 告警触发：NodeDown或服务特定告警
- 监控数据停止更新

### 1.4 CPU高负载故障
**故障描述**：服务器CPU使用率过高，影响服务性能。

**模拟方法**：
- **使用stress工具**：`stress --cpu 4 --timeout 60`
- **使用bash循环**：`for i in {1..4}; do while true; do :; done & done`
- **编译大文件**：`gcc -O0 -c large_file.c`

**预期现象**：
- Prometheus告警：HighCPUUsageCritical
- 系统响应缓慢
- 服务处理延迟增加
- 可能导致其他服务性能下降

### 1.5 内存不足故障
**故障描述**：服务器内存使用率过高，导致服务性能下降或崩溃。

**模拟方法**：
- **使用stress工具**：`stress --vm 2 --vm-bytes 1G --timeout 60`
- **创建大数组**：Python脚本创建大数组占用内存
- **启动多个内存密集型进程**

**预期现象**：
- Prometheus告警：HighMemoryUsageCritical
- 系统出现OOM（Out of Memory）错误
- 进程被OOM Killer终止
- 服务响应缓慢或崩溃

### 1.6 日志风暴故障
**故障描述**：应用程序产生大量日志，导致日志采集和存储压力过大。

**模拟方法**：
- **快速生成日志**：`for i in {1..10000}; do echo "test log $i" >> /var/log/test.log; done`
- **配置应用程序产生大量日志**
- **模拟错误日志爆发**

**预期现象**：
- Loki存储快速增长
- Promtail采集延迟增加
- 日志查询性能下降
- 可能导致磁盘空间快速耗尽

## 2. 标准化故障排查流程

### 2.1 故障响应流程
1. **告警接收**：通过钉钉等渠道接收告警通知
2. **告警确认**：确认告警的真实性和影响范围
3. **故障分类**：根据告警类型和严重程度进行分类
4. **启动排查**：按照标准化流程进行故障排查
5. **故障解决**：实施解决方案，恢复服务
6. **故障复盘**：记录故障原因、解决方案和经验教训

### 2.2 通用排查步骤

#### 2.2.1 信息收集
- **查看告警信息**：获取告警的详细信息，包括告警名称、严重程度、持续时间等
- **查看监控数据**：通过Grafana仪表盘查看相关指标数据
- **查看日志**：通过Loki查询相关日志信息
- **查看系统状态**：使用系统命令查看系统状态（top、free、df、netstat等）

#### 2.2.2 故障定位
- **确认故障范围**：确定故障影响的范围和程度
- **定位故障根因**：通过指标和日志分析，定位故障的根本原因
- **验证故障假设**：通过实验验证故障假设

#### 2.2.3 故障解决
- **制定解决方案**：根据故障根因制定解决方案
- **实施解决方案**：执行解决方案，恢复服务
- **验证解决结果**：验证服务是否恢复正常

### 2.3 专项故障排查流程

#### 2.3.1 网络故障排查
1. **检查网络连通性**：`ping`、`telnet`、`nc`命令测试网络连通性
2. **检查网络接口**：`ip addr`、`ifconfig`查看网络接口状态
3. **检查路由表**：`route -n`、`ip route`查看路由表
4. **检查防火墙规则**：`iptables -L`、`firewall-cmd --list-all`查看防火墙规则
5. **检查网络流量**：`tcpdump`、`wireshark`捕获和分析网络流量

#### 2.3.2 磁盘故障排查
1. **检查磁盘空间**：`df -h`查看磁盘使用情况
2. **检查磁盘I/O**：`iostat`、`iotop`查看磁盘I/O情况
3. **检查大文件**：`find / -type f -size +100M`查找大文件
4. **检查日志文件**：`du -sh /var/log/*`查看日志文件大小
5. **检查文件系统**：`fsck`检查文件系统完整性

#### 2.3.3 服务故障排查
1. **检查服务状态**：`systemctl status`、`docker ps`查看服务状态
2. **检查服务日志**：`docker logs`、`journalctl`查看服务日志
3. **检查服务配置**：查看服务配置文件是否正确
4. **检查服务依赖**：检查服务依赖的其他服务是否正常
5. **检查资源使用**：`top`、`docker stats`查看服务的资源使用情况

#### 2.3.4 CPU高负载排查
1. **查看CPU使用情况**：`top`、`htop`查看CPU使用情况
2. **查看进程列表**：`ps aux --sort=-%cpu`查看CPU使用率高的进程
3. **查看进程线程**：`pstree -p`查看进程的线程情况
4. **分析进程**：`perf`工具分析进程的CPU使用情况
5. **检查定时任务**：`crontab -l`查看是否有定时任务导致CPU高负载

#### 2.3.5 内存不足排查
1. **查看内存使用情况**：`free -h`、`top`查看内存使用情况
2. **查看进程内存使用**：`ps aux --sort=-%mem`查看内存使用率高的进程
3. **查看内存泄漏**：`valgrind`工具检查内存泄漏
4. **检查缓存使用**：`vmstat`查看内存缓存使用情况
5. **检查OOM日志**：`dmesg | grep -i oom`查看OOM Killer日志

## 3. 快速恢复方案

### 3.1 网络故障恢复
- **恢复网络接口**：`ifup eth0`或`ip link set eth0 up`
- **移除防火墙规则**：`iptables -D INPUT -s 192.168.213.142 -j DROP`
- **恢复网络延迟**：`tc qdisc del dev eth0 root`
- **重启网络服务**：`systemctl restart network`或`systemctl restart networking`

### 3.2 磁盘空间恢复
- **清理临时文件**：`rm -rf /tmp/*`、`rm -rf /var/tmp/*`
- **清理日志文件**：`truncate -s 0 /var/log/syslog`或`echo "" > /var/log/syslog`
- **删除大文件**：`rm -f /tmp/bigfile`
- **清理Docker镜像和容器**：`docker system prune -a`
- **扩展磁盘空间**：添加新磁盘或扩展现有磁盘

### 3.3 服务崩溃恢复
- **重启容器**：`docker restart prometheus`
- **重启服务**：`systemctl restart prometheus`
- **恢复数据**：从备份恢复数据
- **重新部署服务**：使用Docker Compose重新部署服务
- **检查服务配置**：修复服务配置问题后重启服务

### 3.4 CPU高负载恢复
- **终止异常进程**：`kill -9 <pid>`或`pkill -9 <process_name>`
- **停止stress工具**：`pkill stress`
- **调整进程优先级**：`renice -n 19 <pid>`降低进程优先级
- **扩展服务器资源**：增加CPU核心数或升级CPU
- **优化应用程序**：优化代码，减少CPU消耗

### 3.5 内存不足恢复
- **终止内存占用高的进程**：`kill -9 <pid>`
- **停止内存密集型应用**：停止消耗大量内存的应用程序
- **清理缓存**：`sync; echo 3 > /proc/sys/vm/drop_caches`
- **扩展内存**：添加更多物理内存
- **优化内存使用**：优化应用程序的内存使用

### 3.6 日志风暴恢复
- **停止产生日志的应用**：临时停止产生大量日志的应用
- **清理日志文件**：`truncate -s 0 /var/log/test.log`
- **调整日志级别**：将应用程序的日志级别调整为WARN或ERROR
- **配置日志轮转**：配置logrotate自动轮转和清理日志
- **增加存储容量**：扩展Loki的存储容量

## 4. 故障预防措施

### 4.1 监控告警优化
- **合理设置告警阈值**：根据实际情况设置合理的告警阈值，避免误报和漏报
- **配置告警抑制规则**：避免告警风暴，提高告警准确性
- **定期测试告警**：定期测试告警规则，确保告警正常触发
- **优化告警通知**：确保告警通知能够及时送达相关人员

### 4.2 资源管理优化
- **设置资源限制**：为容器和服务设置资源限制，避免资源耗尽
- **配置自动扩展**：根据负载自动扩展资源
- **定期清理资源**：定期清理临时文件、日志文件和过期数据
- **监控资源使用**：实时监控资源使用情况，及时发现资源瓶颈

### 4.3 配置管理优化
- **版本控制配置**：使用Git等版本控制系统管理配置文件
- **配置备份**：定期备份配置文件，便于恢复
- **配置验证**：在部署前验证配置文件的正确性
- **配置变更管理**：实施配置变更管理流程，避免配置错误

### 4.4 高可用性设计
- **冗余部署**：关键服务采用冗余部署，提高可用性
- **负载均衡**：使用负载均衡器分发流量，提高系统可靠性
- **故障自动切换**：配置故障自动切换机制，减少停机时间
- **定期备份**：定期备份数据，确保数据安全

### 4.5 运维自动化
- **自动化部署**：使用Ansible、Terraform等工具实现自动化部署
- **自动化监控**：配置自动化监控，及时发现和处理问题
- **自动化恢复**：配置自动化恢复脚本，实现故障自动恢复
- **自动化测试**：定期进行自动化测试，验证系统功能

## 5. 故障案例分析

### 5.1 案例1：磁盘空间满导致服务崩溃
**故障现象**：监控系统告警显示磁盘使用率超过90%，随后Prometheus服务崩溃。

**故障根因**：Loki日志存储快速增长，导致磁盘空间耗尽，Prometheus无法写入数据而崩溃。

**排查过程**：
1. 查看磁盘使用情况：`df -h`显示根目录使用率95%
2. 查找大文件：`du -sh /loki/*`发现Loki存储占用了大量空间
3. 查看Loki日志：发现应用程序产生了大量错误日志

**解决方案**：
1. 清理过期日志：配置Loki的数据保留策略，自动清理过期日志
2. 调整日志级别：将应用程序的日志级别从INFO调整为WARN
3. 扩展磁盘空间：添加新磁盘并挂载到Loki存储目录

### 5.2 案例2：CPU高负载导致监控延迟
**故障现象**：监控数据更新延迟，Grafana仪表盘显示数据滞后。

**故障根因**：服务器CPU使用率持续超过90%，导致Prometheus无法及时采集和处理数据。

**排查过程**：
1. 查看CPU使用情况：`top`显示多个stress进程占用了大量CPU
2. 查看进程列表：`ps aux`发现是测试脚本启动的stress进程
3. 查看系统负载：`uptime`显示系统负载超过CPU核心数

**解决方案**：
1. 终止stress进程：`pkill stress`
2. 优化监控采集频率：将Prometheus的scrape_interval从15s调整为30s
3. 增加服务器资源：升级服务器CPU或添加新服务器

### 5.3 案例3：网络中断导致监控失效
**故障现象**：Prometheus Targets页面显示所有目标为DOWN状态，监控数据停止更新。

**故障根因**：防火墙规则配置错误，导致监控系统无法与被监控对象通信。

**排查过程**：
1. 测试网络连通性：`ping 192.168.213.141`显示网络不通
2. 检查防火墙规则：`iptables -L`发现添加了错误的DROP规则
3. 检查路由表：`route -n`确认路由配置正确

**解决方案**：
1. 移除错误的防火墙规则：`iptables -D INPUT -s 192.168.213.142 -j DROP`
2. 配置正确的防火墙规则：只允许必要的端口和IP访问
3. 验证网络连通性：`ping 192.168.213.141`确认网络恢复正常

## 6. 总结

通过建立完善的故障模拟、排查和恢复机制，可以有效提高监控系统的可靠性和稳定性。关键要点包括：

1. **故障预防**：通过合理的监控告警、资源管理和配置管理，预防故障的发生
2. **快速响应**：建立标准化的故障响应流程，确保故障能够及时被发现和处理
3. **准确定位**：通过系统的排查步骤，快速定位故障的根本原因
4. **快速恢复**：制定有效的恢复方案，确保服务能够快速恢复正常
5. **持续改进**：通过故障复盘和经验总结，持续优化监控系统和运维流程

通过不断完善故障排查体系，可以提高运维人员的故障处理能力，减少故障对业务的影响，保障监控系统的稳定运行。
